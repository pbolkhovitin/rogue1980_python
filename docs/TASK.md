# Задание: Разработка Rogue 1980 на Python

## Анализ задания и MVP

Задание требует реализовать roguelike-игру на Python 3.10 с curses, строго следуя механикам Rogue 1980 с описанными упрощениями. Основная часть – Задания 0–5. Дополнительные Задания 6–9 не обязательны, их исключаем из MVP.

### Ключевые требования MVP:

1. **Чистая архитектура**: domain (бизнес-логика, сущности, генерация, бой, ходы), presentation (curses-рендеринг, ввод, туман войны, интерфейс), data (JSON-сохранение прогресса и статистики).

2. **21 уровень**, каждый – 9 комнат + коридоры, связный граф. Стартовая комната (без врагов) и конечная (с переходом). Генерация случайная, но детерминированная (seed не требуется, но карта сохраняется).

3. **Персонаж**: здоровье (hp), максимальное здоровье (max_hp), ловкость (dex), сила (str), текущее оружие (может быть None). Рюкзак: отдельные слоты для еды, эликсиров, свитков, оружия (макс. 9 каждого типа; сокровища накапливаются отдельно, слота не лимитированы, но хранятся как одно число).

4. **Предметы**: еда (восстанавливает hp), эликсиры (временно повышают dex/str/max_hp на N ходов), свитки (постоянно повышают dex/str/max_hp), оружие (даёт бонус к силе, влияет на урон). Сокровища – только с врагов, идут в рейтинг.

5. **Противники**: 5 видов (Зомби, Вампир, Привидение, Огр, Змей-маг) с уникальными характеристиками и паттернами движения.

6. **Бой**: при движении на клетку с врагом. Этапы: проверка попадания, расчёт урона, смерть, выпадение сокровищ.

7. **Сложность**: растёт с уровнем (количество врагов, их сила, количество и типы предметов).

8. **Пошаговость**: ход игрока → все враги совершают действие.

9. **Сохранение**: после каждого уровня сохраняется полное состояние. При запуске – предложить новую игру или продолжить.

10. **Статистика**: таблица рекордов всех попыток.

11. **Рендеринг**: туман войны, ray casting + Брезенхэм для видимости.

12. **Управление**: WASD – движение; h – оружие, j – еда, k – эликсиры, e – свитки. Выбор предметов по номеру 1-9.

## Архитектура проекта

```
src/
├── domain/          # бизнес-логика, сущности, генерация, бой, ходы
│   ├── entities/    # Character, Player, Enemy, Item, Tile
│   ├── generation/  # генерация уровней, комнат, коридоров
│   ├── combat.py    # расчет hit/damage, apply_attack
│   ├── ai.py        # паттерны движения врагов
│   └── fov.py       # ray casting, Брезенхэм
├── presentation/    # curses-рендеринг, ввод, туман войны, интерфейс
│   ├── renderer.py  # абстрактный Renderer, Renderer2D
│   ├── input.py     # обработка WASD, h/j/k/e, цифр
│   └── ui.py        # статус-бар, инвентарь, меню, статистика
├── data/           # JSON-сохранение прогресса и статистики
│   └── game_data_manager.py
├── utils/          # константы, Tile, Position, Direction
└── config.py       # флаги BONUS_*
```

## Правила разработки для агента opencode

### Роли и поведение
- **Архитектор**: следит за соблюдением слоёв (domain не импортирует presentation/data). Использует dependency injection.
- **Разработчик**: пишет код с type hints, docstrings, именами по PEP8.
- **Тестировщик**: создаёт unit-тесты на каждую новую функцию (pytest). Покрытие критических путей >80%.
- **Документатор**: обновляет README и внутреннюю документацию при изменении интерфейсов.

### Технические скилы
- Python 3.10, стандартная библиотека (curses, json, random, collections, itertools, typing).
- Для работы с картой: list comprehension, BFS/DFS, A* (опционально).
- Формулы расчёта: хиты, урон, генерация подземелий.
- Работа с curses: цветовые пары, stdscr.getch(), stdscr.addstr(), обновление экрана.

### Правила написания кода
- **Модульность**: каждый файл – не более 300 строк. Одна сущность – один файл.
- **Типизация**: все аргументы и возвращаемые значения аннотированы. Использовать `from __future__ import annotations`.
- **Имена**: snake_case для функций/переменных, PascalCase для классов, UPPER_SNAKE_CASE для констант.
- **Документация**: у каждого публичного метода и класса – docstring.
- **Обработка ошибок**: не использовать голые `except:`, перехватывать конкретные исключения.
- **Состояние**: избегать глобальных переменных; всё состояние хранить в объектах.

### Требования к тестам
- Для каждой функции в domain – тест на граничные случаи.
- Тесты генерации: проверять связность графа, отсутствие пересечений комнат.
- Тесты боя: проверять формулы попадания, урон, особые способности.
- Запуск тестов перед каждым коммитом (через pre-commit).

### Коммиты и ветки
- Работать в ветке `develop`. Каждая задача – отдельный коммит с сообщением в формате: `[этап N] краткое описание`.
- Не пушить в master. В конце проекта – pull request с проверкой.
- Коммиты должны быть атомарными.

### Критерии приёмки
- Код проходит `mypy --strict` (кроме curses-обёрток).
- Код проходит `pytest` без ошибок.
- Игра запускается и позволяет пройти хотя бы 3 уровня без краша.
- Сохранение и загрузка работают.
- Статистика записывается и отображается.

## Расширяемость для бонусов (Задания 6-9)

Хотя бонусы исключены из MVP, архитектура должна позволять их добавить без переписывания:

1. **Tile** вместо простых символов (поддержка дверей, ключей).
2. **BalanceAdjuster** сервис (динамическая балансировка).
3. **EnemyFactory** с поддержкой Mimic (мимик).
4. Паттерн Strategy для **Renderer** (2D/3D переключение).
5. Флаги `BONUS_*` в `config.py` для условной активации.

При всех `BONUS_* = False` код должен работать и не требовать наличия бонусных модулей.
